# 01.5 — Repository Visibility & Missing-Source Analysis

Determine the application's repository scope when the developer's local working tree is a partial, sparse, or otherwise incomplete checkout.

**Analysis/documentation task only. Do NOT modify application source code.**

## Objective

Prompt 01 analyzes the source available in the current working tree. This prompt fills architectural blind spots caused by source that exists in Git but is not checked out locally.

The goal is **not** to create a full local checkout.

Instead:
- keep the developer's existing working tree unchanged
- discover what exists beyond the local checkout
- selectively inspect relevant source from Git when safely accessible
- identify important areas that remain unavailable
- provide Prompt 02 with a reliable repository-visibility baseline

## Rules

- The local working tree is the developer's active development scope, NOT proof of the application's complete repository scope.
- Do not assume a directory/file absent from the working tree does not exist.
- Do not perform a full checkout merely for analysis.
- Do not change sparse-checkout rules, switch branches/worktrees, reset files, or otherwise disturb the developer's working state.
- Prefer read-only Git inspection.
- Use available local Git objects/repository metadata first.
- When relevant source is outside the working tree, inspect it selectively through Git when the required objects are locally available or a narrow read-only remote mechanism is safely available.
- Do not fetch or retrieve the entire repository simply because a dependency is missing.
- If relevant source cannot be accessed without broad retrieval, mark it **Unverified** and state exactly what could not be checked.
- Never fabricate missing architecture, dependencies, modules, tests, or behavior.
- Do not place sensitive repository contents into generated documentation.
- Use these evidence labels:
  - **Confirmed — Local**: verified from the checked-out working tree.
  - **Confirmed — Git**: verified from repository source outside the working tree.
  - **Inferred**: derived from available evidence.
  - **Unverified**: important source/evidence could not be accessed.

## 1. Determine local checkout scope

Inspect:
- repository root
- current branch/worktree
- Git status
- remotes
- sparse-checkout configuration where present
- locally visible projects/directories
- build/test/configuration areas present locally

Establish whether the working tree appears to be full, sparse/partial, or otherwise intentionally limited.

Do not confuse a project being absent locally with it being absent from the repository.

## 2. Determine broader repository scope

Use read-only Git inspection to identify:

Preferred mechanisms, when supported by the local repository setup, include:
- `git ls-tree` to inspect repository tree contents without checking them out
- `git show <ref>:<path>` to read a specific tracked file without placing it in the working tree
- `git cat-file` to verify whether an object is locally available before attempting to read it

Use remote access only when it can be done narrowly and read-only. Do not use a broad fetch/checkout simply to make the whole repository available.


- projects/directories present in relevant repository refs but absent locally
- shared/common projects
- other production modules
- NRT/test modules
- build/deployment/configuration projects
- framework/shared infrastructure
- database-related source
- scripts/tools that may affect runtime behavior

Start with the repository tree. Do not read every file outside the checkout.

## 3. Identify architecturally relevant missing areas

From Prompt 01 and the local code, determine which missing repository areas could affect:
- Simulation
- Credit Risk
- shared application runtime
- shared utilities/framework
- Oracle/Hibernate/JDBC behavior
- Swing/UI behavior
- configuration/security
- build/deployment
- NRT architecture
- cross-module dependencies

Prioritize missing areas that could change architectural or CR-impact conclusions.

## 4. Selectively inspect missing source

For each relevant missing area:
1. Identify the smallest useful set of files.
2. Read those files directly from Git when safely accessible without checkout.
3. Trace only the relationships needed to establish architecture, dependency, or test evidence.
4. Stop expanding once the relationship is sufficiently understood.
5. Record the repository ref/path used as evidence.

Do not materialize an entire missing project into the working tree.

## 5. Compare local vs broader repository evidence

Create a table covering the important missing areas:

| Area | Local visibility | Git visibility | Relevant? | Evidence | Confidence |
|---|---|---|---|---|---|
| Project/module | Local / Missing | Present / Not found / Unavailable | Yes/No | path/ref | Confirmed/Inferred/Unverified |
| Shared dependency | Local / Missing | Present / Not found / Unavailable | Yes/No | path/ref | Confirmed/Inferred/Unverified |
| NRT module | Local / Missing | Present / Not found / Unavailable | Yes/No | path/ref | Confirmed/Inferred/Unverified |
| Build/deployment | Local / Missing | Present / Not found / Unavailable | Yes/No | path/ref | Confirmed/Inferred/Unverified |

## 6. Establish analysis confidence

Explicitly identify conclusions from Prompt 01 that may have been weakened by the incomplete checkout.

Pay particular attention to:
- module maps
- dependency direction
- shared runtime/classpath assumptions
- framework responsibilities
- DB ownership and consumers
- NRT relationships
- build/deployment topology
- cross-module flows
- Simulation/Credit Risk dependencies

Do not invalidate Prompt 01 wholesale. Preserve useful local findings and qualify only the areas affected by missing source.

## 7. Create/update repository visibility reference

Create or update:

docs/architecture/REPOSITORY_VISIBILITY.md

Include:
1. Local checkout scope
2. Repository refs/remotes inspected
3. Projects/modules visible locally
4. Relevant projects/modules found outside the checkout
5. Shared/framework/build/DB/test areas relevant to the application
6. Selectively inspected Git files and what each established
7. Important architecture/dependency conclusions enabled by Git evidence
8. Important source still unavailable
9. Confidence/visibility limitations
10. Guidance for future prompts when relevant source is outside the working tree

Keep this document focused on **source visibility and evidence provenance**. Do not duplicate the full architecture.

## Output

Return:
- Local checkout assessment
- Broader repository assessment
- Relevant missing-source map
- Git evidence inspected
- Prompt 01 findings that need qualification
- Unverified areas
- REPOSITORY_VISIBILITY.md update summary
- Handoff notes for Prompt 02

The final result must make it clear what is known from the local checkout, what is known from Git, and what remains unknown.
