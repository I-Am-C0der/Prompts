# 05.6 — Database ↔ GUI Lineage & Navigation Analysis

Perform the final application-lineage analysis connecting database objects to actual GUI screens, user actions, menu navigation, and reverse data flow.

This is the **final knowledge-base step of the initial application analysis**.

**Do NOT modify application source code.**

## Objective

Build a traceable mapping:

database object -> DB write/read path -> application/business code -> GUI action -> screen -> menu/navigation

and the reverse:

GUI screen/action -> application flow -> persistence path -> database object

The analysis must work when relevant production modules are absent from the local checkout and available through repository source, JARs/classpath artifacts, the GetAllJars module, or packaged configuration/resources.

## Inputs

Use and cross-check, where available:
- outputs from Prompts 01 and 01.5
- architecture documentation
- docs/architecture/REPOSITORY_VISIBILITY.md
- docs/architecture/JAR_AND_BINARY_DEPENDENCIES.md
- docs/architecture/MODULE_DOSSIER_SIMULATION_CREDIT_RISK.md
- local source
- relevant source outside the checkout through read-only Git inspection
- exact JARs/classpath artifacts used by the current build/runtime
- GetAllJars
- bytecode/decompiled code
- Swing screen/action/menu code
- XML/properties/resource/configuration
- wrapper-framework registration
- Oracle/Hibernate/JDBC code
- stored procedures/packages/functions
- views/synonyms/triggers

Re-verify material assumptions rather than blindly trusting earlier documentation.

## Rules

- Analysis/documentation only; do not modify application source.
- Do not require a full repository checkout.
- Do not alter branches, sparse-checkout configuration, worktrees, or build/runtime configuration merely for analysis.
- Treat local absence as different from repository absence.
- Inspect relevant missing source selectively through Git.
- If implementation exists only in a JAR, use the exact artifact actually used by the current build/runtime.
- For Maven, do not substitute the newest artifact for the resolved version.
- For SNAPSHOTs, identify the actual resolved artifact where possible.
- Prefer source evidence; use JAR/bytecode/decompiled/configuration evidence when source is unavailable and label it.
- Never treat decompiled code as equivalent to original source.
- Do not dump entire JARs or decompiled classes into documentation.
- Do not expose secrets, credentials, customer data, production payloads, or restricted configuration.
- Never infer an exact menu path from package/class names alone.
- Never infer a table modification merely because a screen reads/displays the table.
- Distinguish read/display paths from actual write paths.

Use evidence labels:
- Confirmed — Source
- Confirmed — JAR/Bytecode
- Confirmed — Configuration/Resource
- Confirmed — Database
- Inferred
- Unverified

## 1. Establish database-object identity

For a supplied table name, normalize and investigate:
- schema-qualified name
- synonyms
- views and updatable views
- underlying tables
- quoted/case-sensitive identifiers where applicable
- aliases used by application code
- environment-specific schema mappings

Do not stop at a literal table-name search.

## 2. Find every meaningful modification path

Search for:
- INSERT, UPDATE, DELETE, MERGE and other relevant DML
- Hibernate entity persistence
- Hibernate save/persist/update/merge/delete
- HQL/JPQL
- native SQL
- JDBC and CallableStatement usage
- stored procedures/packages/functions
- dynamic SQL
- SQL assembled from strings/configuration
- database triggers
- INSTEAD OF triggers/updatable views
- generic DAO/repository/framework-generated persistence

For every relevant path identify:
- database object
- operation
- Java/application entry point
- transaction boundary where relevant
- direct/indirect mechanism
- side effects
- evidence provenance

Do not equate a SELECT with a modification path.

## 3. Trace write paths back toward the GUI

For every GUI-reachable write path, trace as far back as evidence permits:

database -> SQL/ORM/procedure -> DAO/repository -> service/business logic -> controller/action/listener -> Swing component/screen

Search for:
- ActionListener
- Swing Action
- buttons and toolbar actions
- menu actions
- popup/context-menu actions
- command/controller patterns
- screen/controller/presenter mappings
- event/listener registration
- factories and registries
- screen-opening helpers
- reflection
- configuration-driven mappings
- wrapper-framework entry points

Do not stop at the service layer when a concrete GUI path can be established.

## 4. Identify the exact screen

For each confirmed GUI path determine where possible:
- exact visible screen/window/dialog name
- Swing class name
- technical screen identifier
- module/project
- controller/action class
- relevant button/menu/action label
- save/apply/submit/delete/approve/confirm operation causing the write
- whether the write occurs on open, edit, save, delete, approve, submit, or another action

Prefer actual UI title/label/resource over naming-based guesses.

If multiple screens can reach the same write path, list all confirmed screens.

## 5. Reconstruct exact menu/navigation path

Trace actual menu registration and screen opening.

Inspect where applicable:
- JMenu/JMenuItem
- Swing Action
- menu factories/registries
- XML menu definitions
- properties/resource bundles
- configuration
- wrapper-framework registration
- screen IDs
- screen factories
- reflection/class-name mappings
- role/entitlement controlled menus
- feature flags
- environment-dependent configuration

Produce the exact navigation path using visible labels, for example:

Main Menu -> Operations -> Trade Management -> Trade Amendment

Do not infer menu hierarchy from Java package structure.

Record:
- visible menu labels
- technical IDs/classes where available
- conditions/permissions affecting visibility
- alternative navigation paths
- evidence and confidence

If navigation is dynamic or conditional, state the condition instead of presenting one universal path.

## 6. Reverse analysis: screen -> database

For a supplied screen/class/identifier, trace each meaningful user action and determine:
- reads
- inserts
- updates
- deletes
- merges
- stored procedure calls
- trigger side effects where relevant
- tables/views/synonyms affected
- transaction boundary
- audit/history tables
- related control/reconciliation tables

Separate actions. Do not collapse all persistence into one screen-level statement.

## 7. Table -> GUI result

For a supplied table, return every relevant GUI modification path and include:
- table/schema
- operation
- exact screen name
- user action
- exact menu/navigation path
- module/project
- complete application call chain
- JAR involved, if applicable
- persistence mechanism
- procedure/trigger/view involvement
- transaction boundary where relevant
- evidence provenance
- confidence

List confirmed non-GUI writers separately, including batch, scheduled, background, database procedure, and trigger paths.

## 8. GUI -> table result

For a supplied screen, return:
- how the screen is opened
- all confirmed navigation paths
- relevant user actions
- tables/views/synonyms read
- tables affected by DML
- indirect DB effects
- audit/history/control objects
- procedures/packages/functions
- relevant NRT tests where identifiable

Separate display-only actions from persistent actions.

## 9. JAR and GetAllJars analysis

When source is unavailable locally:
1. Identify the exact artifact used by the current build/runtime.
2. Check GetAllJars for the applicable artifact.
3. Inspect JAR contents selectively.
4. Inspect relevant classes with bytecode tools such as javap or safe decompilation when necessary.
5. Inspect packaged resources that may define GUI/menu/navigation behavior.
6. Trace additional JARs only as far as necessary.
7. Cross-check binary-derived behavior against source/configuration/database evidence.

Check for:
- duplicate classes
- conflicting versions
- classpath ordering
- compile/runtime version differences
- wrapper-framework registrations
- menu/screen resources
- service/provider registrations
- reflection mappings

If the exact binary cannot be established, mark it Unverified.

## 10. Dynamic and indirect behavior

Explicitly investigate cases where simple text search can fail:
- dynamic SQL
- table names from configuration
- procedure names from configuration
- reflection
- class names in properties/XML
- generated Hibernate SQL
- generic DAO/repository frameworks
- screen factories
- generic menu registries
- event buses/listeners
- wrapper-framework metadata
- database triggers
- synonyms/views
- environment-specific configuration

State when static analysis cannot prove the final runtime target.

## 11. Permissions and conditional navigation

Where supported by evidence, identify:
- role/entitlement requirements
- menu visibility conditions
- feature flags
- module enablement
- environment-specific menu configuration
- actions restricted by state/context

Do not infer permissions from names alone.

## 12. Domain, transaction, and operational context

Where relevant, connect the lineage to existing application evidence for:
- business/trade/settlement/value dates
- calendars/holidays/cut-offs/time zones
- currencies/units
- precision/rounding
- state transitions
- reconciliation/control totals
- audit/history
- approvals/entitlements
- batch/end-of-day dependencies
- duplicate-processing prevention

For confirmed write paths, also capture where relevant:
- Hibernate flush/session behavior
- JDBC connection/commit/rollback
- procedure transaction behavior
- trigger side effects
- locking/concurrency
- partial-update risk
- retry/idempotency behavior
- user-visible success/failure

Do not invent business rules.

## 13. NRT and test lineage

Connect relevant GUI actions and persistence paths to:
- corresponding NRT module
- JUnit classes/cases
- fixtures/test data
- DB/integration dependencies
- coverage gaps

Do not use test existence as proof of full GUI/DB coverage.

## 14. Evidence and confidence matrix

Use:

| Finding | Evidence type | Exact evidence | Confidence | Limitation |
|---|---|---|---|---|
| Screen name | Source/JAR/Config | class/resource | Confirmed | — |
| Menu path | Source/JAR/Config | menu registration | Confirmed | condition if any |
| DB write | Source/JAR/DB | DML/procedure/ORM | Confirmed | — |
| Indirect side effect | DB/JAR/Source | trigger/call chain | Confirmed | — |
| Runtime-only behavior | — | insufficient evidence | Unverified | what is missing |

Do not upgrade an Inferred finding to Confirmed merely because several indirect clues agree.

## 16. Reusable future queries

The final knowledge base should make these queries answerable without rediscovering the architecture:
- Which GUI screens modify table X?
- How do I navigate from the main menu to the screen that modifies table X?
- Which menu/action opens screen Y?
- Which tables can screen Y modify?
- Show the call chain from screen Y to table X.
- Does table X have non-GUI writers as well?
- Which NRT tests protect the screen/action that modifies table X?
- Is the relevant implementation in source, Git, or a JAR?
- What permissions/conditions are required to reach the screen?
