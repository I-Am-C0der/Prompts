# 05.6 — Final Knowledge-Base Consolidation & On-Demand Traceability

Finalize the initial application knowledge base after Prompts 01–05.5.

**This is a finalization task, not an exhaustive database-to-GUI mapping task.**

Do NOT attempt to enumerate every table, screen, menu item, or GUI-to-database relationship in the application.

## Objective

Make the existing architecture knowledge base sufficient for Claude Code to answer targeted questions quickly and accurately later, such as:
- Which GUI screen modifies table X?
- How do I navigate to that screen?
- Which tables does screen Y modify?
- Show the call chain from screen Y to table X.

Do this by documenting **how the application can be traced**, where the important trace anchors live, how source visibility works, and how JAR-backed modules should be inspected on demand.

The final result should reduce future rediscovery without performing a repository-wide lineage scan.

## Inputs

Use and reconcile:
- outputs from Prompts 01 and 01.5
- architecture documents created by Prompt 02
- CLAUDE.md from Prompt 03
- findings from Prompt 04
- code-review guidance from Prompt 05
- `docs/architecture/REPOSITORY_VISIBILITY.md`
- `docs/architecture/JAR_AND_BINARY_DEPENDENCIES.md`
- `docs/architecture/MODULE_DOSSIER_SIMULATION_CREDIT_RISK.md` when present
- available local source
- relevant Git-visible source outside the working tree
- the application's JAR/classpath artifacts
- `GetAllJars` or equivalent binary collection
- build/configuration/resource files

## Rules

- Do NOT modify application source code.
- Do NOT perform a full repository checkout.
- Do NOT enumerate all database tables and GUI screens.
- Do NOT attempt exhaustive table -> screen or screen -> table mapping.
- Do NOT crawl every JAR or every package simply to build an inventory.
- Do NOT alter branches, sparse-checkout configuration, worktrees, or build/runtime configuration.
- Prefer existing evidence produced by Prompts 01–05.5.
- Perform only targeted verification needed to determine reusable tracing mechanisms and anchors.
- Use read-only Git inspection for missing source where needed.
- When binary-only dependencies are relevant, use the exact resolved artifact already established by Prompt 05.5.
- Never substitute a newer Maven artifact merely because it exists.
- Never treat decompiled code as equivalent to original source.
- Do not copy secrets, credentials, customer data, production payloads, or restricted configuration.
- Distinguish facts from reusable tracing guidance.

## 4. Define the targeted table -> GUI tracing algorithm

Create a concise, reusable procedure for future on-demand queries:

1. Normalize the table/schema name.
2. Locate real write mechanisms: DML, Hibernate, JDBC, procedures, views, triggers, dynamic SQL.
3. Identify the owning application component and call chain.
4. Determine whether the path is GUI, batch, scheduled, background, or database-only.
5. For GUI paths, trace backward through controller/action/listener code.
6. Resolve the exact Swing screen/window/dialog.
7. Trace screen registration/opening to the actual menu/action configuration.
8. Report the exact visible navigation path only when supported by evidence.
9. Consult Git/JAR evidence when relevant code is outside the local checkout.
10. State conditions, permissions, alternatives, and Unverified links explicitly.

The procedure should tell Claude **where to look first** based on the architecture discovered in the initial analysis.

## 5. Define the targeted GUI -> database tracing algorithm

Create the reverse procedure:

1. Resolve the exact screen/class/identifier.
2. Find the relevant user actions.
3. Trace action -> controller/service -> persistence.
4. Identify actual DML/ORM/procedure behavior.
5. Separate reads from writes.
6. Identify indirect effects such as triggers, audit/history, or procedures.
7. Identify the exact DB objects affected.
8. Consult NRT information where needed.

Again, provide reusable search/tracing anchors rather than precomputing all relationships.

## 6. Define source/JAR/configuration fallback order

Document a preferred evidence order for future targeted lineage requests:

1. Local source
2. Local build/classpath configuration
3. Exact resolved JAR
4. JAR resources/configuration
5. JAR bytecode/decompiled implementation
6. Relevant source from Git outside the working tree
7. Oracle metadata/configuration where accessible
8. Runtime evidence only when available

The actual order may be adjusted when the application's discovered architecture requires it. Explain the reason for any deviation.

Never silently fall back to guesswork.
