# 05.5 — JAR & Binary Dependency Analysis

Analyze relevant compiled Java dependencies that are available as JARs or other binary artifacts but whose source is not present in the local working tree.

**Analysis-only/documentation task. Do NOT modify application source code.**

## Objective

Legacy Java applications often compile against modules whose source is not checked out locally. A class or method used by the active module may exist only inside a JAR. Do not treat the absence of source as the absence of implementation.

The goal is to selectively recover enough binary-level evidence to understand relevant dependencies without checking out unrelated projects.

## Rules

- Do not modify application source code.
- Do not require a full repository checkout.
- Do not alter branches, sparse-checkout configuration, worktrees, or build configuration merely for analysis.
- Inspect local JARs/classpath artifacts before declaring a relevant dependency Unverified.
- Prefer the exact JAR version actually used by the current build/runtime.
- Use read-only tools such as `jar`, `javap`, and safe decompilation when available.
- Inspect only the classes/packages needed to establish the relevant dependency or behavior.
- If a required JAR exists only in Git, inspect it through Git without checking out the whole project when practical.
- If a required binary exists only in an external artifact repository or environment that is inaccessible, record it as Unverified rather than guessing.
- Never treat decompiled code as equivalent to original source.
- Do not copy secrets, credentials, production data, or restricted binary contents into documentation.

Use evidence labels:
- **Confirmed — Source**: verified from source code.
- **Confirmed — JAR/Bytecode**: verified from compiled binary contents.
- **Confirmed — Metadata**: verified from JAR/build/classpath metadata only.
- **Inferred**: derived from available evidence.
- **Unverified**: required evidence could not be accessed.

## 1. Identify relevant binary dependencies

Inspect the active project's:
- build files and dependency declarations
- IDE/project classpath files
- `lib`/`libs` directories
- application launch scripts
- runtime classpath configuration
- packaging/deployment configuration
- local dependency caches where relevant
- JAR manifests and version information

Identify JARs that provide classes referenced by the locally available application code.

## 2. Verify the exact artifact

For each materially relevant JAR determine where possible:
- file path
- version/build identifier
- manifest metadata
- origin or dependency declaration
- package/class supplied
- whether multiple versions are present
- whether compile-time and runtime versions could differ

Prefer the artifact actually used by the current build or runtime configuration over a similarly named JAR.

## 3. Inspect JAR structure

Use JAR metadata to determine:
- packages
- classes
- interfaces
- superclasses
- related helper classes
- embedded resources when relevant
- service-provider registrations
- manifest classpath entries
- module metadata when present

Do not scan unrelated packages simply because the JAR is large.

## 4. Inspect relevant classes and methods

For each relevant dependency:
1. Locate the exact class.
2. Inspect method signatures and inheritance using bytecode/class metadata.
3. Inspect bytecode or decompiled implementation when the implementation affects architecture, correctness, transactions, threading, security, or CR blast radius.
4. Trace calls into other classes only as far as necessary.
5. Check exceptions, synchronization/threading, static state, DB access, framework calls, and side effects where visible.

A method signature alone is not sufficient evidence when implementation behavior materially affects the analysis.

## 5. Java 8 / legacy-specific binary checks

Where relevant, inspect for:
- Java class-file version compatibility
- interface vs implementation assumptions
- overloaded/overridden methods
- static initializers
- singleton/static state
- synchronization/threading
- reflection
- service-loader registrations
- framework annotations or registrations
- JDBC/ORM usage
- Swing/EDT interaction
- wrapper-framework hooks
- dependency on other JARs
- binary compatibility hazards
- duplicate classes across JARs
- classpath ordering hazards
- linkage/error risks caused by version mismatch

Do not claim runtime behavior that cannot be established from available evidence.

## 6. Trace the dependency into the application

Build targeted relationships such as:

`local caller -> external class -> external method -> relevant side effect/dependency`

Where applicable also trace:
- other local callers of the same binary class
- relevant JAR-to-JAR dependencies
- DB/persistence behavior
- framework/security behavior
- shared runtime state
- NRT/test implications

Do not attempt to reconstruct the entire JAR ecosystem.

## 7. Assess source-vs-binary confidence

For each important conclusion state whether it is based on:
- local source
- JAR metadata
- bytecode
- decompiled code
- build/classpath evidence
- inference
- unavailable evidence

Call out cases where decompilation may omit source-level detail that would matter to the conclusion.

## 8. Create/update durable binary-dependency reference

Create or update:

`docs/architecture/JAR_AND_BINARY_DEPENDENCIES.md`

Include:
1. Relevant JARs/binary artifacts
2. Artifact/version/source of evidence
3. Important classes/packages provided
4. Local source callers
5. Important inspected methods/behavior
6. JAR-to-JAR dependencies where relevant
7. Binary compatibility/classpath risks
8. Runtime/build/deployment implications
9. NRT implications where relevant
10. Source/binary confidence and remaining unknowns

Keep this document selective. It is a dependency/evidence map, not a dump of decompiled code.

## Output

Return:
- Relevant JAR inventory
- Exact artifact/version evidence
- Important classes/methods inspected
- Dependency and behavior findings
- Source-vs-binary confidence
- Binary compatibility/classpath risks
- NRT/release implications
- Unverified binary areas
- `JAR_AND_BINARY_DEPENDENCIES.md` update summary
- Handoff guidance for future CR/code-review prompts

The final result must make clear which behavior was verified from source, which was verified from JAR/bytecode, and which remains unverified.
